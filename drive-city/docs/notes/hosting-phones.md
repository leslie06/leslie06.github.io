# Static hosting, boot time, loading bar, phones, touch

Moved verbatim from CLAUDE.md on 2026-10-13. Dated entries say when and why (the user's words in 「」).

- `ui/Touch.ts` — on-screen controls for phones, auto-detected from a coarse pointer with touch points (`?touch=1` forces them on, `?touch=0` off). A floating stick on the left half, pedals and buttons bottom-right, a drag anywhere else to look. It writes into `Input.touch`, which `poll` merges with the keyboard and pad, so no other module knows about touch. The body gets `dc-touch` (never `touch`: the root element uses that class and would pin the body), which shrinks the speedo, radar and top-right readouts; pointer lock is skipped on touch.
- Pitfall (static hosting): a dev server swallows sixty parallel image requests; GitHub Pages queues them on one HTTP/2 connection. Unthrottled, the first live load took 178 s to become playable, with single textures stalled over two minutes and one `ERR_HTTP2_PROTOCOL_ERROR`. Three changes were needed, in this order of impact: `city/Materials.ts` no longer awaits the photo sets, so materials start as flat colours and take their maps when they arrive (only the facade's brick and plaster are awaited); `core/Assets.ts` allows four image requests in flight; `nav/index.ts` holds its 718-file map crawl until 20 s after `game:start` or the moment the map opens. `scripts/deploy.mjs` also drops the ao and disp maps and halves normals and roughness, taking the published build from 70.9 MB to 18.7 MB. Measure a deploy with `node .scratch/boottime.mjs <url>`, which prints time-to-playable and the slowest resources; the local dev server will not show this.
- Pitfall (static hosting, round two): after all that, the live build still took 72-85 s to become playable. `node .scratch/waterfall.mjs <url>` prints the live request waterfall (start, queue, duration, size) and what was in flight when a given request went out, which is what found it: the tile worker's 42 KB module script was requested only at 28 s - `city/index.ts` awaited `createCityMaterials`, which waits for the two facade photo sets - and then took 42 s to arrive behind 10 MB of images, finishing 1.5 s before the boot did. No tile can be meshed without a worker, so the whole boot sat on it. `city/index.ts` now calls `spawnTileWorkers()` (exported by `city/Streamer.ts`) before its `Promise.all`, so that fetch goes out while the connection is still idle; the `CityStreamer` constructor takes the workers it made. Cutting the worker count would not have helped: all four share one module fetch and wait on the same response.
- Pitfall (static hosting, round three, 2026-09-27/28): the eight new Blender landmarks and the trees added ~11 MB that all started downloading at boot, and the live game went from 48 s to 166 s to playable. The glb landmarks and the Blender trees now wait for the spawn's tiles (`placeLandmarks`' gate, `CityStreamer.loadTrees()`), then the landmarks go nearest the spawn first, two at a time. Compared on the same throttled link (both builds served locally, `KBPS=500 node .scratch/livetime.mjs <url>` - it prints ms to load, ready, trees, landmarks): the previous deploy 43.1 s to ready, this one 40.6 s, the landmarks all in at 74 s. And a download that failed used to stay failed: on a flaky connection (`ERR_HTTP2_PROTOCOL_ERROR` on GitHub Pages) 祈年殿 never came and left a hole (its footprint had removed the OSM building), the trees fell back to the procedural ones, the player's model to the crowd's. `core/Retry.ts` `retry()` now tries the landmark glbs, the tree atlas and trees.json and the player's model three times (3 s, then 6 s apart); the player's model also counts a texture that failed inside GLTFLoader (which only warns) as a failed attempt. `node .scratch/retryprobe.mjs [url]` drops the first request of five of them and checks each arrives.
- Pitfall (static hosting, round four, 2026-10-02): the live game took 221 s to playable on a slow link after the step-4 data went into the boot. Measured with `MODE=play KBPS=500 node .scratch/bootbytes.mjs <url>` (the real game, ready = `window.drivecity`; without `MODE=play` it is shot mode, whose ready also waits for the player's model) - it lists what downloads before ready, grouped by size - against the previous deploy served locally (`node <scratch>/serve.mjs <dir> <port>`, a static server that gzips like Pages): **`network.json` and `manifest.json` were fetched twice** (the city and `Materials.ts`' far road mask each called `loadCity`; it now caches the promise per file, forgetting a failure); the guide signs and the railways load after the boot (`DEFER_EXTRAS`, not in shot mode unless `?defer`), once the player starts or 20 s on, and the railways' street clearing reaches the tiles already built through `CityStreamer.addStreetClear` (each tile it reaches is built again; the old one stays drawn and solid until the new one is in, colliders swapped in the same step, the vegetation pools refilled); `rail.json` is simplified (Douglas-Peucker 0.25 m / 0.1 m) and delta-coded in decimetres (`v: 2`, `decodeRail`: 1.46 MB / 456 KB compressed -> 265 / 87 KB); every photo texture but the facade's brick and plaster is asked for only once the spawn's tiles are in (`createCityMaterials(.., later)`); the player's normal maps are JPEG (1.56 MB of PNG -> 0.29 MB). Real game at 500 KB/s: 26.4 -> 16.9 s to ready, 11.1 -> 6.4 MB before it; shot mode 42.6 -> 31.5 s. `node .scratch/latextras.mjs` checks the late extras arrive and rebuild tiles without errors.
- The loading bar (2026-10-12, 「游戏加载添加游戏进度」): `index.html`'s inline script draws a bar, a percentage and the stage from the first byte (`window.__boot`: `stage(from, to, label, secs)` - a span of the bar it creeps through at about that pace, never reaching its end - and `sub(f)`, the stage's own fraction, whichever is further); `core/Boot.ts` `boot.stage/sub` report from `main.ts` and `city/index.ts` (the city's files counted by weight as they arrive, the spawn's tiles from `CityStreamer.preload`'s progress callback). The spans are measured at 80 KB/s (GitHub Pages from China): the program 0-27% (15 s), the engine 27-55% (16 s: Rapier's wasm), the map data 55-85% (17 s), the streets 86-96% (6 s), the rest; re-measure with `KBPS=80 node .scratch/bootbar.mjs <url> outPrefix [phone]` against a build served by `node .scratch/serve.mjs /Users/kangyu/ai-games 5298` (gzips like Pages) after changing what the boot loads.
- Pitfall (static hosting, round five, 2026-10-03): measured from the user's own machine, the live site gave 50-70 KB/s (GitHub Pages from China), so 5.3 MB before ready was 90 s (116 s on an emulated iPhone; `node .scratch/waterfall.mjs <url>` showed a link busy end to end, not stalls). Cut what the boot waits for: the facade's brick and plaster photos are no longer awaited (the facade starts on a neutral grey - an sRGB 128 texel equal to the fallback mean; it was linear, 2.3x too bright - and a flat normal map, so the swap is a uniform change: `userData.setFacadeTex`; shot mode still awaits them); the far skyline loads right after the spawn's tiles (`putSky`); the car bodies load the saloon and the wheels (and the body of the player's saved car, from `drivecity.garage.v1` / `drivecity.home.v1`) before the world and the rest after the spawn's tiles (`readyBodies(types)`, `bodySettled`): traffic fills the other bodies' places with stand-in saloons and swaps them as each body arrives, parked hatchbacks wait for theirs, police builds the SWAT kit once the SUV is in (a kit built before would stay procedural); `network.pack.json` v2 delta-codes the edges' ends (0.97 -> 0.87 MB). The map's crawl got a 404 every boot for a block of roads only (`-12_9`): every block with a tile now has a file. At 100 KB/s, real game: 64.6 -> ~40 s to ready, 5.7 -> ~3.5 MB before it (`MODE=play KBPS=100 node .scratch/bootbytes.mjs <url>`, both builds served by `<scratch>/serve.mjs`). Left: Rapier's compat build embeds its wasm as base64 (1.08 MB gzipped against 0.77 for the raw .wasm, if Pages compresses wasm - unverified), the bundled stunt/heli/rabbit models (~180 KB gzipped, their call sites build visuals and colliders together), and the host itself: a server or CDN near the players is the one big lever left. `node .scratch/bodymix.mjs` checks the real game's traffic gets every body after boot.
- Pitfall (phones): the render budget is `maxPixels`, not `pixelRatio` - capping both starves a phone of resolution. A 3x iPhone in landscape is 750x342 CSS pixels, so `low`'s `pixelRatio: 1` (plus a `coarse ? 1.3` clamp on dpr) drew 0.26 MP and let the browser blow it up 3x onto a 2250x1026 screen - one rendered pixel per nine physical ones, and six times *under* low's own 1.6 MP budget. That was the whole of 「手机上画面特别差，看不清楚」. Every tier now renders at `min(devicePixelRatio, 2)` and `maxPixels` alone does the budgeting, which is bit-for-bit unchanged wherever the window is big enough for that cap to bind (1920x1080 at low is ratio 0.879 either way, and a retina desktop at high still lands on exactly 3.6 MP). The phone buffer goes 750x342 -> 1500x684 at a held 60 fps. `minRenderScale` is 1 on low (0.75 until 2026-09-25) for the same reason: 4x the pixels cost only +32% of a frame there because a low-tier frame is fixed-cost bound (~200 draw calls), so shedding pixels buys the governor almost nothing - and a real phone that could not hold 60 was parked at 0.75, a 2x upscale, which was 「画面特别差，画面不清晰」 the second time. Low also has 1024 photo maps (the deployed files are 1024, so nothing more downloads; was 512), anisotropy 8 and a CAS sharpen (0.3, without the chromatic aberration high adds). `node .scratch/phonelook.mjs out.png [params]` screenshots an emulated iPhone at full device resolution (`SCALE=0.75` forces the render scale). Rotation: the engine follows the container with a ResizeObserver plus orientation / visualViewport events and late re-checks - window 'resize' alone fires on iOS before the page is laid out again, so the landscape picture kept the portrait aspect (the car stretched sideways, 「刚开始车很宽」) until the governor next resized; `node .scratch/rotateprobe.mjs` rotates an emulated iPhone and also changes the container with no event at all. Measure with `node .scratch/mobprobe.mjs` (emulated iPhone/Pixel + a retina desktop: tier, buffer, upscale factor, governor scale) and `node .scratch/mobcost.mjs` (frame cost at ratio 1/1.5/2/2.5/3 on one phone-sized page).
- 启动减重第 6 轮（2026-10-17，「接着把启动减重做了」；起因是看板上中位活跃 29 秒，线上到标题前要下 7.0 MB）：新写的 `KBPS=150 node .scratch/boot/wf.mjs <url> [phone]` 按时间列出到标题画面为止的每个请求和游戏自己记的启动阶段（`window.__stat`，见 `online.md` 的漏斗；脚本总是带 `?nostat&lb=0`，不往线上统计发数据）。测本地构建用 `node .scratch/serve.mjs <目录> <端口>`（现在和 Pages 一样带 `cache-control: max-age=600`）。找到并改了四处：
  - **延后加载开始得太早**：树、远景天际线、照片贴图、地标 glb、其他车身原来在出生点街区加载完就开始下，和标题前还要的小文件抢带宽——`combat` 安装时等的 2 KB `cast.json` 排了 9 秒。现在 `core/Boot.ts` 有 `afterTitle`（标题画面出现时 `boot.titleShown()` 放行），正常游戏里这些都等它（`city/index.ts` 的 `later()`、`main.ts` 的 `readyBodies()`）；路牌和铁路原来是「进城或 20 秒后」，20 秒从城市安装算起，慢网速下在标题之前，现在从标题算。截图模式照旧立刻加载。`combat` 也不再等 `cast.json`：哪些打手有模型等清单到了再填，之前开打的用人群身体。
  - **物理引擎的 wasm**：rapier compat 版把 2 MB wasm 用 base64 塞在 JS 里，压缩后 1029 KB；`vite.config.ts` 的 `rapierWasmFile` 插件在构建时把它另存成 `assets/rapier-<哈希>.wasm`（压缩后 743 KB，Pages 会 gzip `application/wasm`），初始化改成 `fetch` 它。开发服务器和测试还用内嵌的。
  - **分块 worker 脚本下了 4 遍**：4 个 worker 同时启动各下一遍（4×59 KB）。现在先起一个，回了 ping（`tileWorker.ts` 认 `{ping}`）再起其余三个，读缓存。**坑**：`new Worker(new URL('./tileWorker.ts', import.meta.url))` 必须整个写在一起，拆开 Vite 就不把它打成 worker，而是把 `.ts` 源文件原样发出去，worker 起不来，分块等满 60 秒超时。
  - **meshoptimizer**：`from 'meshoptimizer'` 会带上编码器、聚类、切线（各自内嵌 wasm），车身又多一份解码器。现在车身用 three 自带的解码器（`Bodies.test.ts` 真解码 `.bin`，45 条过），`KitLod` 只引 `meshoptimizer/simplifier`。主程序压缩后 1029 → 996 KB。
  - 结果（本地构建，同一台机器同时测）：150 KB/s 到标题 45.0 → 33.1 秒，60 KB/s 108.5 → 77.2 秒；标题前下载 5.05 → 3.93 MB。标题出来后 `node .scratch/boot/after.mjs <url> outPrefix [KBPS]` 检查树、地标、路牌、天际线都陆续到齐并截图。
  - `network.pack.json`（1.43 MB）试过改二进制只小约 10%，不值得。
- 内嵌 JSON 模型改成标题后加载（2026-10-18，「把内嵌的 JSON 模型也改成标题后加载」）：`core/Late.ts` 的 `late(load, use)`——正常游戏里等 `afterTitle` 再 `import()`（每个 JSON 成为单独的 chunk），截图模式立刻加载，并且 `ShotMode` 要等 `lateSettled()` 才算 ready。改了四个：特技道具 `stunts/models.json`（106 KB，`loadPropModels`；`Jumps.ts` 的坡道、烂尾高架和土堆先记下 `todo` 再放，`underground` 的车库模型、`Shortcuts.ts` 的灯笼——先只有木柱，模型到了把灯笼合进每个门的网格）、直升机 `heli.json`（48 KB，网格先是空几何体）、生活道具 `life/props.json`（20 KB）、兔儿爷 `rabbit.json`（18 KB）。**碰撞体都还是安装时建**，只是外观晚几秒。摩托 `moto.json`（55 KB）没动：交通在路边随时生成摩托、车库里玩家的车也可能是摩托，加载完之前没有替代模型，出错就是崩。主程序压缩后 996 → 795 KB；60 KB/s 到标题 77.2 → 73.8 秒（主程序下完 19.6 → 16.2 秒）。验证：`node .scratch/boot/latecheck.mjs <url> outPrefix`（真实帧循环：标题时各模型的顶点数应该是 0，8 秒后到齐，再到坡道、捷径、兔儿爷跟前截图）、`node .scratch/boot/helicheck.mjs <url> outPrefix`（三星通缉时直升机有几何体）。
- 国内镜像（2026-10-18，「继续下一步」，选了「现有阿里云服务器」）：
  - **为什么**：埋点上线后 47 次打开，34 次开始下载城市数据、只有 24 次加载出出生点街区；第一次来的 13 次里 7 次停在这一步。程序要下 27–53 秒，下载速度中位数约 70 KB/s，最慢的 8 KB/s。不走代理直连实测同一个 3 MB 的城市文件：GitHub Pages 58.7 秒（50 KB/s），阿里云服务器 0.56 秒（5.5 MB/s）。**坑**：这台开发机开着 7890 端口的代理，`curl` 默认走代理，两边一样快，测国内速度要加 `--noproxy '*'`，Playwright 加 `--no-proxy-server`。
  - **怎么做**：页面地址不变，还是 GitHub 上的 `index.html`。它开头的脚本在中国时区（`Asia/Shanghai` 等）的浏览器里插一个 `<base href="https://stats.fishai.asia/bcity/">`，所有相对地址（程序、城市数据、模型、贴图、配音、wasm）就都从镜像取。`?cn=1` 强制走镜像（本地测构建用），`?cn=0` 不走。
  - **跨域 worker**：`new Worker(跨域地址)` 会直接报错，所以开头的脚本包了一层 `window.Worker`：跨域时建一个同源的 blob，里面写 `import "<镜像地址>"`。worker 里的地址要用绝对地址传进去：`Streamer` 和 `MapData` 原来写的是 `new URL(…, location.href)`，改成 `document.baseURI`。
  - **预加载扫描器**：浏览器在开头的脚本运行之前，就按页面原地址抢先下了 Vite 注入的 `index-*.js` 和 `three-*.js`，国内白从 GitHub 下约 0.9 MB。`vite.config.ts` 的 `bootTagsLate` 在构建时把这两个标签收进 `<template data-boot>`（扫描器不看 template），head 末尾再由 `__bootTags()` 插回去。**坑**：插件按最后一个 `</head>` 插入，注释里写了 `</head>` 字样的话，用第一个就会插错地方。
  - **退回 GitHub**：程序入口（`assets/index-*.js`）加载失败时，去掉 `<base>`、从 GitHub 再取一次（`host: "cn>gh"`）；本来就在 GitHub 上的，过 1.5 秒加个参数重取一次。这一条也是为了埋点里看到的 `rerr`（入口文件没下载下来，页面一直是空的）。只有入口失败才换；入口取到了、之后某个数据文件失败的，还是由 `Retry.ts` 重试同一个地址。
  - **Radio**：`createMediaElementSource` 接跨域的 `<audio>` 时，不设 `crossOrigin = 'anonymous'` 就是静音。
  - **服务器**：Caddy 在 `stats.fishai.asia` 下加了 `handle_path /bcity/*` → `/srv/bcity`，带 `Access-Control-Allow-Origin: *`；`/assets/*` 缓存一年（文件名带哈希），其余文件 10 分钟（和 GitHub 一样）。改之前的备份是 `/etc/caddy/Caddyfile.bak-20261018`。
  - **部署**：`npm run deploy` 末尾用 rsync 同步到 `/srv/bcity`，整份传约 20 秒（`--delete`，上一版的程序文件在 `bcity/` 里留着）。必须在推送 GitHub 之前传完。`NO_MIRROR=1` 跳过这一步。macOS 自带的 openrsync 不支持 `--chmod`，所以传完再用 ssh 跑一次 `chmod -R a+rX`。**坑**：本地连着部署两次、中间没推送时，「上一次部署」是没上线的那次，线上页面正在用的 `index-*.js` 被当成上上版删了。现在 `git show HEAD:bcity/deploy-assets.json` 列出的线上文件也从 git 里取出来留着。
  - **埋点**：`__stat.host` 记 `cn` / `gh` / `cn>gh`；看板漏斗加了「国内镜像」「GitHub」两个分组。
  - **测试**：`node .scratch/serve.mjs ../bcity 5298`，然后 `node .scratch/cnprobe.mjs "http://127.0.0.1:5298/?cn=1&nostat&lb=0&lang=zh&intro=0&resume=0" [block]`：走真实帧循环，从标题进城、开车、开地图，按来源统计请求。`cn=1` 时除了页面本身全部来自镜像（468 个请求，69 MB）；加 `block` 拦掉镜像，会换回页面原地址（`cn>gh`）。
- 手机帧率（2026-10-18，「继续下一步」）：
  - **为什么**：埋点里手机占一半流量，但 15 次手机会话没有一次玩满 3 分钟。两台 Mali-G76 安卓手机在最低画质下第一分钟的帧率中位数只有 25 和 19，最低一成掉到 14 和 9；iPhone 同样是最低画质，有 42 帧。
  - **卡在 CPU，不是 GPU**：`node .scratch/phone/perf.mjs <url> [CPU 降速倍数] [秒] [参数]` 模拟 851×393、DPR 2.75 的安卓横屏手机，触屏、最低画质，从标题进城开车，每半秒记一次帧间隔、`engine.cpuMs`（新加的：每帧从开始到提交完渲染命令的 JS 时间）、draw call、缓冲区和 renderScale。CPU 降速 4 倍时 35 帧，降速 6 倍时 19 帧（正好对上那两台 Mali），而且 `cpuMs` 几乎等于帧间隔，所以降分辨率没用。`prof.mjs` 按系统拆每帧的 CPU 时间，`cpuprof.mjs` 用 CDP profiler 列函数热点，`draws.mjs` 把一帧的 draw call 按物体分组，`scene.mjs` 数场景里的物体。**坑**：这台机器后台负载高的时候（load average 15 以上：系统设置在扫描存储），同一配置连测两次能差 20%。要比较就把改前、改后各构建一份（`git worktree add` 出 HEAD 再 `vite build --outDir`），用 `serve.mjs` 起在两个端口上，交替各跑 3 轮。
  - **空的实例化网格**：一帧 410 次 draw call 里有 151 次（主画面 93、阴影 58）是实例数为 0 的实例化网格，主要是车辆按车身和 LOD 各建了一份、当时没用上的那几份。three 对这种网格照样切着色器、传 uniform、绑缓冲区，最后画 0 个实例。`core/Engine.ts` 包了一层 `renderer.renderBufferDirect`：实例数为 0 的直接跳过（three 对 drawCount 为 0 的几何体也是这么处理的）。
  - **路边停着的摩托**：交通池里停着的载具（主要是路边摩托，最多 5 辆）原来每个固定步都跑完整的车辆物理。现在站稳一秒后让 Rapier 刚体睡眠，并跳过 `step`（`traffic/index.ts` 的 `nap`）；被撞或被推时 Rapier 会把它唤醒。**坑**：判断静止要看水平速度，`car.speed` 静止时是 0.061（竖直方向那个 −0.375·g·dt）。路边停的汽车归 `parking/` 管，那边本来就便宜。`node .scratch/phone/parked.mjs <url> [outPrefix]`：路边车会睡下；开车撞上去会醒、被推开，6 秒后又睡下；走过去按 F 能抢走开走。
  - **省电档 `engine.lite`**：在最低画质下，进城后帧率中位数连续两段（每段 240 帧）低于 40 帧就自动打开，并记在本机（`drivecity.lite.v1`）。打开后，交通车和骑手的上限各减半，路人少生成三成，小地图 15 Hz，不画阴影。阴影的做法是停掉阴影贴图更新（`shadowMap.autoUpdate = false`），再在 `Lighting.setKey` 里把 `shadow.intensity` 这个 uniform 设成 0。不能关 `shadowMap.enabled` 或 `castShadow`：材质要换 program，而 program key 在第一次打补丁时就冻结了。**坑**：一次都没画过的阴影贴图没有渲染目标，阴影采样器绑上的是空贴图，WebGL 会拒绝所有受光照材质的 draw，画面只剩天空。所以停止更新之前，要先 `needsUpdate = true` 让它画一次。`node .scratch/phone/look.mjs <url> outPrefix` 在同一位置分别截省电档开和关的画面。各模块读 `engine.lite`，或者听 `'quality:lite'` 事件。`?lite=1` 强制打开；`?lite=0` 关掉、清掉本机记录，这次也不自动打开。帧率越低，每帧要补跑的 60 Hz 固定步越多，交通车的物理开销跟着成倍涨：CPU 降速 6 倍时，关掉交通能从 20 帧升到 30 帧。`node .scratch/phone/liteauto.mjs <url>` 测自动打开、重开后保留、`?lite=0` 清掉这几种情况。
  - **结果**（改前、改后各构建一份，交替各跑 3 轮）：CPU 降速 6 倍（相当于那两台 Mali 手机）时，改前 62 ms（16 帧），改后 53 ms（19 帧），省电档 40 ms（25 帧）。降速 4 倍时，三种版本的中位数分别是 33.8、31.9、24.3 ms，那次测的时候机器负载高，单次读数波动很大。省电档里最大的一项是交通：帧率越低，每帧补跑的固定步越多。下一步还能做的是：远处交通车用更便宜的物理；远处地标的矩阵不再每帧重算（场景 2733 个物体里有 2390 个每帧重算，大多是远处地标）。
  - **埋点**：漏斗多了 `cpu`（第一分钟每帧 JS 时间的中位数）和 `lite`（省电档打开的时间；开局就是省电档的记 0）。以后看到 `fps` 低的会话，可以对一下 `cpu`：接近 1000/fps 就是 CPU 瓶颈。
- 手机标题画面看不到「进入城市」（2026-10-18，「继续下一步」）：埋点里有好几次手机会话到了标题画面却没进城，苏州那台华为待了 45 秒，江门那台 Mali 待了 8 分多钟。用模拟手机（851×393 横屏、触屏）只靠触屏走第一分钟（`node .scratch/phone/first.mjs <url> <outDir>`：进城、按住油门、摇杆转向、开关地图、刹车下车、走路，每步截图）发现，标题画面右边整块是键盘操作卡片（W/S、A/D、空格、鼠标……）。原来的 `@media (max-height: 470px)` 紧凑布局只在宽度 ≤ 820 时才藏这张卡片，而现在很多手机横屏宽 844–851。卡片高 782 px，把菜单撑高，「进入城市」掉到 y=393，正好在屏幕下边缘之外，要在菜单里往下滑才看得到，可菜单上没有任何提示。现在触屏（`body.dc-touch`）和矮屏都不显示这张卡片；触屏标题画面换成一行触屏操作提示（`title.touch`：左半屏拖动转向，摇杆按下才出现）。`node .scratch/phone/titledom.mjs <url> [宽 高]` 列出标题画面每个按钮的位置、有没有出屏、有没有被挡（`OUT=x.png` 同时截图）：851×393、844×390、740×360、390×844 下都在屏幕里，不用滑动。
